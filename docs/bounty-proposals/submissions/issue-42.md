## Bounty 02 — Clear view of active rules

Please review the proposed account lookup and confirmed rule receipts for #42.

In the block 29 report, `checktx` admitted the signed op-0 rule, `gettxstatus` showed confirmation, the sender paid 10 AGRS, and the accumulated text looked unchanged. Subsequent fixes hard-reject a rule that fails to land at live apply and expose rejection details. Two questions remain for a transaction that *does* confirm. What changed when that transaction executed? Which conditions protect the account at the current head? This proposal targets `tau-testnet` at `c2b8c47` and its pinned Tau engine at `c3ea334`. A private prototype and its tests predate maintainer approval. [Original report](https://github.com/IDNI/tau-testnet/issues/42#issue-5367387633) · [Maintainer’s remaining cases and native probe](https://github.com/IDNI/tau-testnet/issues/42#issuecomment-5853846245)

### What the wallet reads

```text
getactiverules <sender> [recipient] [--tx <hash>] [--payment <id>]
getrulesnapshot <block_hash> status
getrulesnapshot <block_hash> <content_id> [byte_offset]
```

The first response identifies the genesis, canonical block hash, height and active consensus ID. Each account’s outgoing clause and rule-change guard come from the registry used by execution. An installed slot carries its exact UTF-8 body and SHA-256 digest. An empty supported slot returns `absent`. The baseline protocol reports incoming enforcement as `unsupported`. With recipient controls installed and activated, the recipient’s entry also exposes its incoming clause, policy digest and hold caps. Bob’s outgoing limit applies when Bob spends.

Suppose Alice installs a limit early in block 81 and replaces it later in that block. Both transactions can confirm and charge fees. For the first transaction, the wallet matches the account and target stream 5, then compares the receipt’s `new_body_sha256` with the current `sender.outbound.body_sha256`. If the query’s head is block 81 and the digests differ, it can show “Installed in block 81 and replaced later in the same block.” A null new digest records removal. Today `getruleoffers` can show the registered slot and `gettxstatus` can confirm inclusion. Separate calls can observe different heads, and neither establishes the first transaction’s effect. [Upstream registry lookup](https://github.com/IDNI/tau-testnet/blob/c2b8c47e07342dee01ac27f1380872374e3bf6ff/commands/getruleoffers.py) · [Wallet walkthrough](https://github.com/947822urhbfhu/tau-testnet/blob/9a6f77615055aba609fff2d433c2f692e5dbeeea/docs/bounty-proposals/checking-a-rule-installation.md#verify-an-installation-in-the-proposed-interface)

### Why the native rule view matters

Apply `o26=7 && o27=9`, then `o26=3`. Both updates genuinely change the specification. The interpreter subsequently produces **3 and 9**. Searching submitted text still finds the obsolete 7. Declaring the first submission entirely superseded would lose the surviving 9. A revision counter distinguishes two revisions but cannot tell the wallet which clause survived.

One specification part can also retain several alternatives. Tau tries them in priority order and executes the first solvable alternative. Different inputs can change that choice at the same revision. The pinned Python `current_spec()` calls `api::current_spec()`, which can print a disjunction even after execution. The proposed read-only `current_spec_parts()` returns each conjunctive part and its ordered formulas. A separate `current_selected_spec()` exposes the C++ step observation with its time point. With an older binding the node advertises `selected_step_only` and returns `parts = null`. A wallet can still verify account slots and must label the shared view as partial. The snapshot also includes the representation plan and typed mappings for interned identifiers. Preflight remains necessary for a concrete payment whose verdict depends on its inputs, balance or history. ### Commit, reorg and restart

Record the accepted execution’s charged fee, transaction position, ordered effects and bounded diagnostics in the canonical block transaction. `gettxstatus` gains `rule_outcome` for confirmed transactions. A shared revision records its submitted digest, native outcome and before/after revisions. `ACCEPTED_NOOP` means the native engine accepted delivery and its revision stayed unchanged. The fee field reports what execution actually charged. Registry installs, offers, guarded requests and later releases have distinct effects. Join a release by request ID and canonical ancestry. Discard rejected candidate effects. A transaction absent from the selected branch returns `not_confirmed` in the combined lookup. For an older confirmed transaction without retained execution evidence, return `not_recorded`. The prototype cannot reconstruct the missing block 29 receipt from the fee alone.

Read both accounts, payment details, receipt and shared reference from one database snapshot. Exclude intermediate states during fork replay. A separate worker verifies journal links, replays recorded observations under the committed representation and checks the revision and time point. Reading the live evaluator directly would couple wallet queries to a mutable process during block production. Materializing a full document on every commit would put export work on the write path even on nodes serving no wallets. The prototype starts one reader on demand and retains eight snapshots. A failed reconstruction leaves registry and receipt queries available. A wallet encountering `VIEW_UNAVAILABLE` during a chain switch retries the lookup. Poll a building snapshot at its named block. Follow page offsets and verify the SHA-256 of the assembled bytes. A retained cursor survives a head extension. On `STALE_VIEW` after an orphan or eviction, restart from the account lookup. These are full-node observations. The content digest lets clients verify the assembled pages. Independent validation uses a second node at the same block. Deployment requires a schema upgrade and the native accessor for full coverage, with no new block fields or genesis reset. [Atomic commit](https://github.com/IDNI/tau-testnet/blob/c2b8c47e07342dee01ac27f1380872374e3bf6ff/db.py#L913) · [Authority reconstruction](https://github.com/IDNI/tau-testnet/blob/c2b8c47e07342dee01ac27f1380872374e3bf6ff/tau_authority.py#L236)

The optional payment ID covers an open retractable transfer, including its parties, amount and release point. A programmable grant is a separate object. To assess Bob’s grant-funded payment to a shop, read the grant and any shared allowance, Bob’s outgoing policy and the shop’s incoming policy at matching genesis and block hashes. Retry on head movement and preflight the actual draw. The prototype supplies current grant reads. A historical grant query would need an additional design. [Conditional-grant walkthrough](https://github.com/947822urhbfhu/tau-testnet/blob/9a6f77615055aba609fff2d433c2f692e5dbeeea/docs/bounty-proposals/reading-a-conditional-grant.md#read-one-canonical-head)

### Verification and decisions

Two disposable node servers agreed on the signed installation, its clause digest, block and 10-unit test fee. The follower imported through normal block ingestion and reproduced the receipt and shared document after restart. With recipient controls active, both verified the outgoing clause and 17-block incoming hold cap from one transaction. The harness exercised wallet TCP and delivered the block locally. The native tests used a source build of the patched pinned interpreter. The standalone image build exhausted local storage. [Private testnet observations](https://github.com/947822urhbfhu/tau-testnet/blob/9a6f77615055aba609fff2d433c2f692e5dbeeea/docs/bounty-proposals/design-evidence.md#active-rules)

The final mock run passed 4,536 tests and 32 subtests, with 281 skipped and two configured deselections. The native node CI selection passed 126 tests with two configured deselections. The companion C++ suite passed 30 cases and 241 assertions, with two optional cases skipped.
